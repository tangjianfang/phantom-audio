RFC: Windows 纯软件虚拟 USB 音频设备（UAC 仿真测试台）

需要你

评审人（驱动组 + 测试组）在 2026-11-05 前确认 M0 前置验证排期，以及第三方组件 usbip-win2（BSD-2-Clause）的使用边界（仅内部测试，还是允许随包分发）

Summary#

本方案在单台 Windows 上纯软件仿真指定 VID/PID 的 UAC1/UAC2 USB 音频设备，替代真实声卡/麦克风硬件做主机侧音频软件测试。虚拟 USB 主控复用已签名的开源 usbip-win2（UDE 框架，零内核开发），设备模型为用户态自研。

评审需决定两件事：等时链路这一最高风险是否按 M0 前置验证；第三方组件 usbip-win2（BSD-2-Clause）是否仅限内部测试使用（若要随包分发，只需随附其版权声明与许可条款）。

TL;DR
  • 零内核开发：虚拟 USB 主控用现成已签名驱动（usbip-win2，UDE 框架），设备模型全部在用户态，可脚本化。
  • 被 Windows 内置类驱动（usbaudio.sys / USBAC2.sys）按真设备绑定，被测软件看到的就是"真 USB 声卡"。
  • 最高风险：等时传输（音频端点必需）在 usbip-win2/UDE 上的成熟度未证实，M0 用 Linux 内核 f_uac2 做链路探针，1-2 天出 Go/No-Go。
  • 音量+/静音等设备侧按键事件通过 UAC 规范的 AC 中断端点 Status Word 通知实现，这是内核 f_uac2 做不到、必须自研用户态模型的核心原因。

Motivation#

测试主机侧 USB 音频软件（设备枚举、音量控制、静音、采样率切换、设备事件响应）当前依赖真实 USB 声卡与麦克风硬件，存在四个问题：

  1. 型号与标识固定：真实设备 VID/PID、描述符固定，无法模拟目标客户设备或多个机型。
  2. 硬件事件难以复现：设备侧"音量+ / 音量- / 静音"按键依赖人工操作，无法精确回归。
  3. 异常场景缺失：控制请求异常响应、延迟、断连等故障剧本无法用正常硬件构造。
  4. 台架成本：采购、接线、插拔磨损与多台架管理成本随回归规模线性增长。

需求方明确要求：纯软件、Windows 上实现、可指定 VID/PID、支持 UAC1/UAC2、支持音量/静音等标准功能与硬件事件模拟，仅用于测试替代真实设备。

Goals / Non-Goals#

Goals Non-Goals
R1 纯软件单机：无真实 USB 设备/线缆 不做真实物理 USB 设备仿真（如 Facedancer 硬件路线）
R2 指定 VID/PID 与字符串描述符 不做 UVC 视频设备（架构预留，本期仅音频）
R3 音频输入端点（麦克风 IN）+ 输出端点（扬声器 OUT） 不开发主机侧 USB 驱动：内置类驱动正是被测环境的一部分
R4 UAC1 与 UAC2 双协议档位，被 Windows 内置类驱动绑定 不追求专业音频指标：测试用途，毫秒级抖动可接受
R5 Feature Unit 标准控制：音量 GET/SET、静音、采样率 不支持多设备并发仿真（单设备实例，多实例后续扩展）
R6 模拟硬件事件：音量键经 AC 中断端点主动通知主机 不覆盖 Win10 1903 之前的系统（usbip-win2 下限）
R7 可观测可断言：主机控制请求全量日志，支持错误注入 —

Proposed Design#

图例：颜色仅标系统边界；实线为主路径（枚举、控制、音频流），虚线为配置类路径。全部组件运行在同一台被测 Windows 机器上（自环形态）。

被测软件经 WASAPI 等音频 API 使用设备；Windows USB 栈把仿真器当成一台插在虚拟主控根集线器上的真设备。仿真器内部结构：

需求到组件的映射：

需求 承接组件 / 机制
R1 纯软件单机 UDE 虚拟主控 + 回环 TCP，全程无物理设备
R2 指定 VID/PID 描述符生成器按 Profile 生成设备/配置/字符串描述符
R3 输入+输出端点 AudioStreaming 引擎驱动 AS 接口的一对等时端点（IN/OUT）
R4 UAC1/UAC2 双描述符模板；主机侧分别由 usbaudio.sys（UAC1）与 USBAC2.sys（Win10 1703+，UAC2）绑定
R5 音量/静音/采样率 AudioControl 处理器：Feature Unit 的 Volume（1/256 dB）/Mute，UAC1 端点采样率控制与 UAC2 Clock Source
R6 硬件事件 事件注入器经 AC 中断 IN 端点发送 Status Word（Control Change），主机类驱动查询后回调应用
R7 观测与注入 控制请求全量落日志；错误剧本可对单条请求返回 STALL 或注入延迟

Key Flows#

枚举到类驱动绑定：Windows 把仿真器认成真声卡#

主路径为顺序执行的第 1-9 步；任一描述符请求失败即枚举中断（回退见 Rollout）。

音量控制与设备侧按键事件：双向验证点#

上半段（第 1-5 步）验证主机下发；下半段（第 6-12 步）模拟设备按键并验证主机接收，这是本方案区别于内核 f_uac2 的核心能力。

Alternatives Considered#

Alternative Why not chosen
Linux VM + 内核 f_uac1/f_uac2 + usbip-win2 客户端 保留为 M0 链路探针与降级档：f_uac2 无 AC 中断端点，R6 按键事件无法实现；描述符拓扑固定；VM 依赖使 CI 集成变重
自研 UDE 内核驱动，设备模型内嵌内核 WDF 内核开发、签名与调试成本高一个数量级；仅当等时链路受阻时作为升级路径
商业 USBAnywhere v3.0（WHQL 认证 UDE 方案） 闭源、许可与价格未评估，且不提供可编程设备侧模型与事件注入；列为 R-001 失败时的商业备选
非总线仿真：PortCls/AVStream 虚拟声卡 设备不经 USB 栈枚举，被测软件看到的是非 USB 设备，R4"替代真实 USB 音频设备"即告失败

Risks / Open Issues#

ID Issue / Risk Impact Status Owner
R-001 等时传输成熟度未证实：旧版 cezanne/usbip-win 明确不支持 iso；UDE 文档未覆盖 iso 端点（Microsoft Q&A）；usbip-win2 宣称改进但无音频实测报告 High OpenM0 前置验证 驱动组
R-002 usbip-win2 许可为 BSD-2-Clause（2026-10-30 勘误，原写 GPLv3）：内部测试使用无障碍；若随产品对外分发，需随附其版权声明与许可条款（无源码提供义务） Medium Open 架构 + 法务
R-003 系统版本门槛叠加：UAC2 需 Win10 1703+，usbip-win2 需 Win10 1903+ Low Accepted 驱动组
R-004 用户态 1ms 定时精度：Windows 默认时钟粒度 15.6ms Medium Mitigated：高精度定时器 + 类驱动大缓冲 仿真器组
R-005 Windows 累积更新导致 usbip-win2 兼容性回归 Low Open 驱动组

Rollout & Testing#

里程碑与验收标准（M0 为全案 Go/No-Go 点）：

阶段 内容 验收标准 出口
M0（1-2 天） 链路探针：Hyper-V Linux VM 跑 vudc + f_uac2，Windows 侧 usbip-win2 attach Windows 出现 f_uac2 声卡，播放/录制正常 iso 链路判定：Go 进入 M1
M1（3-5 天） 最小仿真器：静态 UAC1 描述符 + 枚举 + 音量 GET/SET + 正弦等时流 设备管理器出现指定 VID/PID 声卡；主机音量操作被完整记录 R1-R4 达成
M2（3-4 天） UAC2 Profile、采样率切换、AC 中断事件注入 被测软件收到音量变化通知且值一致 R5/R6 达成
M3（2-3 天） 控制 API、Profile 热切换（模拟多机型）、错误注入、CI 脚本 回归用例全绿，含 STALL/延迟剧本 R7 达成

回退路径（失败汇合点）：

  • M0 失败 → 评估 usbip-win2 社区修复可行性 / 商业 USBAnywhere / 升级为自研 UDE 内核驱动（重新评审）。
  • M1-M2 失败但 M0 通过 → 降级为 Linux VM + f_uac2 档位长期运行（放弃 R6，R1 的"单机纯 Windows"放宽为"单机含 VM"）。

验证方式：M0-M3 验收即冒烟；M3 起并入版本回归。断言来源为仿真器请求日志（设备侧）与被测软件行为（主机侧）双向比对。

待确认项#

  • UDE/UdeCx 对等时端点的官方支持口径（Microsoft Q&A 帖待跟进回复）
  • usbip-win2 音频等时链路实测结论（M0 产出物）
  • USBAnywhere v3.0 的等时支持、许可与价格（R-001 失败时的商业备选）
  • 被测软件与仿真器是否同机部署（默认同机自环；异机仅需改 attach 地址）
  • 首批需要模拟的目标设备 Profile 清单（VID/PID、声道、采样率、音量范围）
